# 设置保存逻辑统一化 - 需求文档

## 1. 问题陈述

当前设置界面存在三种不同的保存逻辑，造成用户体验不一致：

### 1.1 当前保存方式

| Tab | 保存方式 | 触发时机 | 用户反馈 |
|-----|---------|---------|---------|
| 常规 | 自动保存 | 开关切换时立即保存 | 无明确反馈 |
| AI | 手动保存 | 点击"保存 AI 配置"按钮 | 按钮点击后有状态文本 |
| 同步 | 混合模式 | 开关自动保存 + "保存配置"按钮 | 混乱 |
| 燕幕/燕选等 | 手动保存 | 点击"保存"按钮 | 按钮点击后保存 |

### 1.2 核心问题

1. **不一致性**：用户不知道哪些设置会自动保存，哪些需要手动保存
2. **冗余按钮**：同步tab既有自动保存又有手动保存按钮
3. **缺少反馈**：自动保存时用户不知道是否已保存成功
4. **操作困惑**：用户可能修改了设置但忘记点击保存按钮

## 2. 用户故事

### US-1: 作为用户，我希望所有设置都能自动保存
**验收标准**：
- 修改任何设置后，无需点击保存按钮
- 设置在修改后短时间内（如1-2秒）自动保存
- 避免频繁保存造成性能问题

### US-2: 作为用户，我希望知道文本设置是否已保存
**验收标准**：
- 点击"保存"按钮后，右上角显示绿色Toast消息
- Toast消息内容清晰（如"AI 配置已保存"）
- Toast消息自动消失（2秒后）
- 开关类设置不显示Toast（状态变化本身就是反馈）

### US-3: 作为用户，我希望操作按钮能自动保存配置
**验收标准**：
- "测试连接"按钮点击时自动保存WebDAV配置
- "立即同步"按钮点击时自动保存WebDAV配置
- 保存成功后显示Toast，然后执行操作
- 保存失败时显示错误Toast，不执行操作

### US-4: 作为用户，我希望开关设置能立即生效
**验收标准**：
- 切换开关后立即保存并生效
- 不显示Toast消息（开关状态本身就是反馈）
- 保存失败时显示错误Toast
- 不需要点击额外的保存按钮

## 3. 功能需求

### FR-1: 统一自动保存机制
**优先级**: P0

所有设置项应采用统一的自动保存机制：
- 使用防抖（debounce）技术，避免频繁保存
- 默认延迟时间：1秒（可配置）
- 窗口关闭时立即保存所有待保存的设置

### FR-2: 保留必要的保存按钮（文本输入类）
**优先级**: P0

**保留保存按钮的场景**：
- ✅ AI tab：保留"保存 AI 配置"按钮
  - 原因：有多个文本输入框，用户需要明确的保存时机
  - 点击后显示Toast："AI 配置已保存"
- ✅ 同步tab：保留"保存配置"按钮
  - 原因：有多个文本输入框和密码框，用户需要明确的保存时机
  - 点击后显示Toast："WebDAV 配置已保存"

**移除保存按钮的场景**：
- ❌ 常规tab：无需保存按钮
  - 原因：只有开关类设置，自动保存即可
- ❌ 其他纯开关类tab：无需保存按钮

**设计理由**：
根据产品研究，文本输入类设置需要保存按钮的原因：
1. 用户可能输入多个字段，需要一次性保存
2. 用户需要明确知道何时保存（特别是密码等敏感信息）
3. 保存按钮 + Toast消息提供了清晰的操作反馈

### FR-3: 添加Toast消息反馈（仅文本输入类）
**优先级**: P0

**设计原则**（基于产品研究）：
- ✅ **文本输入类设置**：需要Toast消息反馈
  - 原因：用户输入后需要明确的保存确认
  - 示例：AI配置（服务地址、API Key、模型名）、WebDAV配置（服务地址、用户名、密码）
- ❌ **开关类设置**：不需要Toast消息
  - 原因：开关本身的状态变化就是明确的视觉反馈
  - 示例：启用同步、开机启动、关闭到托盘等

**Toast消息规范**：
- **位置**：窗口右上角（靠近窗口控制按钮）
- **样式**：绿色背景 + 白色文字 + 勾号图标
- **内容**：简短明确（如"已保存"、"配置已保存"）
- **动画**：从右侧滑入，停留2秒后淡出
- **尺寸**：紧凑型，不遮挡主要内容

**Toast触发时机**：
- 文本输入框失去焦点后1秒（防抖）
- 点击"保存"按钮后立即显示
- 操作按钮（测试连接、立即同步）执行前显示"配置已保存"

### FR-4: 开关类设置的即时保存（无Toast）
**优先级**: P0

开关类设置的特殊处理：
- 切换时立即保存，不使用防抖
- 不显示Toast消息（开关状态本身就是反馈）
- 保存失败时才显示错误Toast

### FR-5: 操作按钮的保存前置
**优先级**: P0

操作按钮在执行前自动保存相关设置：
- "测试连接"按钮：先保存WebDAV配置，再测试
- "立即同步"按钮：先保存WebDAV配置，再同步
- "刷新云状态"按钮：先保存账号设置，再刷新

## 4. 非功能需求

### NFR-1: 性能要求
- 自动保存不应造成UI卡顿
- 使用防抖机制避免频繁I/O操作
- 保存操作应在后台线程执行

### NFR-2: 可靠性要求
- 保存失败时应有明确的错误提示
- 关闭窗口时确保所有设置已保存
- 避免数据丢失

### NFR-3: 用户体验要求
- 保存状态反馈应清晰明显
- 不应打断用户的操作流程
- 保持界面简洁，减少不必要的按钮

## 5. 约束条件

### 技术约束
- 必须兼容现有的 `AppSettingsStore` 保存机制
- 必须支持 WPF 数据绑定
- 必须考虑多线程安全性

### 业务约束
- 不能破坏现有的设置保存功能
- 必须保持向后兼容性
- 迁移过程中不能丢失用户数据

## 7. 优先级排序

### P0 - 必须实现
1. 开关类设置的即时保存（FR-4）
2. 保留文本输入类的保存按钮（FR-2）
3. Toast消息反馈系统（FR-3）
4. 操作按钮的保存前置（FR-5）

### P1 - 应该实现
1. Toast消息动画效果
2. 保存失败的错误Toast
3. 统一的防抖保存机制（FR-1）

### P2 - 可以实现
1. Toast消息队列（多个Toast依次显示）
2. 保存失败重试机制
3. 保存历史记录

## 8. 风险与缓解

### 风险1: 用户不理解为什么有些设置有保存按钮，有些没有
**缓解措施**：
- 遵循行业标准：文本输入有保存按钮，开关无保存按钮
- 提供清晰的Toast反馈
- 在文档中说明设计原理

### 风险2: Toast消息过于频繁打扰用户
**缓解措施**：
- 只在文本输入类设置保存时显示Toast
- 开关类设置不显示Toast
- Toast自动消失时间设置为2秒（不过长）
- Toast位置在右上角，不遮挡主要内容

### 风险3: 保存失败导致数据丢失
**缓解措施**：
- 添加错误处理和错误Toast
- 关闭窗口时强制保存
- 记录保存失败日志
- 保存失败时保留用户输入

## 9. 成功指标

- 用户能清楚知道设置何时保存
- Toast消息提供了清晰的保存反馈
- 开关类设置的即时反馈让用户满意
- 减少因忘记保存导致的设置丢失问题
- 用户满意度提升

## 10. Toast消息设计规范

### 视觉设计
```
┌─────────────────────────────┐
│ ✓ AI 配置已保存              │
└─────────────────────────────┘
```

- **背景色**：`#22C55E`（绿色）
- **文字颜色**：`#FFFFFF`（白色）
- **图标**：勾号 ✓
- **圆角**：8px
- **内边距**：12px 16px
- **阴影**：`0 4px 12px rgba(0,0,0,0.15)`

### 动画效果
- **进入**：从右侧滑入（200ms，ease-out）
- **停留**：2000ms
- **退出**：淡出（200ms，ease-in）

### Toast消息文案
| 场景 | 文案 |
|------|------|
| AI配置保存 | "AI 配置已保存" |
| WebDAV配置保存 | "WebDAV 配置已保存" |
| 测试连接前保存 | "配置已保存" |
| 立即同步前保存 | "配置已保存" |
| 保存失败 | "保存失败：[错误信息]" |
